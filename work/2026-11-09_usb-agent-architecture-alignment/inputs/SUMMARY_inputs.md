# 輸入物摘要

依專案規則，公司內部文件只保存文字摘要，不放原檔。

## 1. 技術團隊架構圖 PPT（USB-Agent 技術架構圖 v8.1，2 頁）

**第 1 頁：技術架構分成 6 層**
- 觸發層、編排層、流程層、工具層、資料層、基礎設施層。
- 9 個智能體一對一綁定 9 條工作流，共 61 個 step：
  coreos_fa、coreos_panic、bundle_verif、efi_proxfw、efi_burnin、diags_fa、diags_panic、efi_validation、efi_diags_rel。
- 工具：61 個模組、87 個函數，自動註冊成 MCP 工具。
- MCP 是獨立的執行平面（port 9000），後端是控制平面（FastAPI，port 8000）。

**第 2 頁：部署架構**
- 三台機器：算力電腦、辦公電腦、工站電腦。
- 算力電腦寫成「GPU 服務器、多模型路由」，和實際的 Mac Mini 不符。
- 辦公電腦和產線網段之間經「網路轉換器」連接。
- 每個工站跑一個 MCP 服務（port 9000），無狀態、只負責執行。

**和程式碼對照後的結論**
- PPT 是目標架構，不是現況。
- 以下幾點和實際程式碼不符：
  - 9 條工作流（實際只有 1 條）；
  - 87 個函數（實際 11 個工具）；
  - 「確定性兜底」（ADR-026 已刪除）；
  - 「交給 LLM 編排」（實際主要路徑是參數直跑）。

## 2. USB-Agent Lite README（實際程式碼）

**規模**
- Python 87 個檔案，15,262 行；216 個測試；27 條 ADR（架構決策紀錄）。

**工作流與智能體**
- 目前只有 1 條工作流：bundle_verification，8 個 step，用 ADK Workflow 的 edges 寫成固定順序。
- 每條工作流配一個 root agent；lead 總助理只聊天，不派發任務。

**兩條執行路徑**
- 參數直跑：產線主要用法，不需要 LLM。
- 自然語言：開發用，需要 LLM。

**工具**
- 11 個工具，回傳值有 pydantic 契約檢查。
- **全部是模擬資料**，沒有一個接過真機。
- 有一層傳輸切換：可在本機直接呼叫，或走 MCP（預設本機）。

**模型與判定**
- 判定採「直出模式」：ADR-026 刪除了三層判定防線。模型呼叫失敗時，流程直接失敗。
- 模型用 httpx 直接呼叫 OpenAI 相容 API。
- 內網 Qwen 必須關閉思考模式，否則會判錯，而且慢 20 倍。

**資料與紀錄**
- ADK session 是唯一事件源；後端只讀，用 SSE 推送給前端。
- 每次測試存成一個資料夾：`logs/workflow/<流程>/`。

**其他規則**
- 機台號一律照用戶原話使用，不猜、不改格式、不預填。

## 3. LabMind 簡報（HH 實驗室 Agent，21 頁）

**定位**
- LabMind 是實驗室的「任務大腦」（專案 PM）。
- 我們的項目在裡面被定義為一個 **LabWork**，負責專業執行。

**四大能力**（第 4 頁）
- 需求承接、任務派發、進度追蹤、成果彙整。
- 首階段不做任務拆解，也不做自動工程驗收。

**和 LabWork 的接法**（第 19 頁）
- 首階段用 A2A 交換任務。
- LabWork 要提供 Agent Card 和服務地址。
- LabWork 要接收任務並回覆是否接受，並回報進度、阻礙和成果。
- 雙方要對齊的業務欄位：來源／目的 Lab、任務與派發編號、目標、期限、承接回覆、狀態版本、成果連結。**其中沒有工作流參數。**

**派發與承接的規則**（第 14～17 頁）
- 首階段派發由人員確認。
- 傳輸成功只代表收到；對方明確接受後，才算建立承接關係。
- 對方可回覆接受、拒絕或補問：拒絕要記錄原因，未回覆就保留等待狀態。
- 重送任務要沿用原派發編號，接收方負責去重。
- 進度用節點和百分比回報。
- 完成和驗收通過分開記錄。

**三類工作**（第 14 頁）
- 新需求、已承接工作（LabWork 主動上報）、跨 Lab 委託。

**Hermes 底座**（第 21 頁，評估中）
- 規劃中的元件：Kanban 調度器（依優先序領取）、Worker 心跳監測、A2A 插件。
- 本輪 Demo 尚未證明 Hermes 已接入執行。

**時程**
- 11/09 Demo 跨 Lab 協作；12/31 試運行，接入真實的 Lab。

## 4. 使用者提供的背景說明（對話中）

**模型與硬體**
- 部署規格：兩台 Mac Mini 組成集群（M4、24G、OS 26.2）。
- 模型：開源的 Qwen3.6-35B-A3B。

**原版工作流出錯與團隊的應對**
- 原版 Bundle 驗證工作流約三萬行。接上模型後，第一個節點的工具回傳結果時就出錯。
- 團隊懷疑是模型跑不動，所以走兩條路線：
  - 蒸餾版：就是上面那份 README；
  - 更輕量的架構：還沒提供。

**工站連線**
- 驗證工作流：用兩個 USB 轉網口連到工站，已驗證能正常刷機。
- Panic 工作流：辦公電腦和 Panic 工站之間無法連網，只能用 USB 串口。實現比較複雜，而且現場已經有自動化，所以優先級調低。
